# Stable phrase-index identities (M07)

Migration 0025 builds a shadow `search_phrase_fts` index over the M06 `(source_kind, chunk_id) → integer row_id` mapping. `search_phrase_content` is an external-content view over current primary/activated chunks. The active replacement has the same public columns and unicode61 tokenizer as the existing phrase index; application queries and rollback code can keep using `search_chunks_fts`.

Source insert/update/delete triggers maintain both substring and shadow phrase postings in the source transaction. Maintenance identifies postings by rowid and supplies the exact OLD token content for deletion. Updates keep the rowid, including a moved chunk; primary/retrieval chunks sharing a string ID have separate rowids. The database prevents retargeting a rowid/source kind. Active flags and unindexed presentation fields come from the current view, so toggling activation does not rewrite token postings. Source deletion/cascades remove postings and identities without depending on trigger execution order. Metadata title/citation/author updates retain their M06 independent document index.

## Online build and cutover

1. Apply 0025 while retaining the old canonical index. Its original maintenance remains active until cutover, so existing readers continue receiving a complete index. There is temporary dual-write and index-storage overhead during this phase. The historical 0008/0010 migrations remain unchanged.
2. `GET /admin/search-index` reports substring and nested `phrase` state. Repeated `POST /admin/search-index/step` with `{}` first completes M06, then visits at most 100 primary/retrieval identities per call for the shadow phrase index. **Both `phase` and `phrase.phase` must be `ready` before the release is considered finished.** Captured IDs bound each batch. Source values are read in the guarded transaction; live inserts below a cursor and edits to already visited rows are maintained by triggers.
3. A 60-second leased owner and transactional guard fence concurrent/stale builders. A transaction advances its cursor only with posting writes. Replay skips `phrase_indexed=1` identities. A final source-to-mapping coverage check precedes cutover. Direct `COUNT(*)` on an external-content FTS table reads its content view and does **not** prove postings coverage.
4. One atomic D1 batch freezes legacy writes, archives the old index as `search_chunks_fts_legacy`, renames the complete replacement to the canonical name, replaces the fixed rowid-maintenance triggers, recreates its vocabulary reader, and marks it ready. Readers observe the old or new schema; there is no half-swapped pointer. Hidden FTS command-column names change on rename, so maintenance triggers are explicitly replaced in that same batch. This small, fixed DDL sequence is maintenance-job work, never normal search-request bootstrap.
5. Failure anywhere in cutover rolls the schema pointer and triggers back. A lost acknowledgment can be retried: the committed ready marker prevents a second rename. An interrupted backfill resumes after its last committed cursor. Expired leases are reclaimable.

## Verification, limits and rollback

Behavioral tests cover fresh install, a 105-document populated upgrade, partial replay, concurrent low-ID insert/edit, transaction failures, cutover rollback/lost acknowledgment, duplicate string IDs across source kinds, stable rowids, active toggles, cascade deletion, generation reprocess/restore, query plans, and external-content integrity checks. A 400-chunk local SQLite fixture took approximately 1.7 ms to delete 10 chunks and 15 ms for 100; these are diagnostic measurements, not production SLOs. Mapping lookup uses the composite unique index; posting maintenance uses a rowid constraint rather than an unconstrained virtual-table delete.

The real disposable workerd/D1/R2 database was upgraded from populated M06, completed the three-step phrase build/cutover, retained before/after literal-phrase document IDs, accepted an idempotent extra step, and indexed a newly reviewed/published document after cutover. The test first uploaded an unreviewed document and correctly observed that it was not publicly searchable; the published fixture then verified literal phrase recall. No production or paid provider calls were made.

Before production cutover, run preview coverage/FTS integrity checks against the real migration/restore shape and compare a representative independently judged holdout, including activated chunks, exact phrases, author/title changes and large reprocess/delete batches. Measure index bytes, dual-write ingestion latency and D1 rows read. The final coverage aggregate is a one-time maintenance check, not a normal search query. M10 extends corruption/restore reconciliation and bounded repair; do not manufacture readiness from a content-view count.

Keep the additive schema and current rowid triggers when rolling back application code. The canonical FTS schema remains compatible with the prior reader. The legacy archive is a frozen cutover snapshot, **not** a current write target: never rename it back over the active table after new writes without rebuilding/reconciling it from authoritative sources under a maintenance plan. Retain it until parity, backups and the rollback window are accepted. Its duplicated text remains storage overhead until an operator explicitly retires it; this change does not silently purge rollback evidence. Do not roll schema back under active writers.
