# Ingestion retry and source revision contract (M22)

Public JSON and multipart ingestion now require a UUID `Idempotency-Key` header (or `idempotencyKey` field). Generate and persist it **before the first attempt**, then reuse it with identical bytes and metadata after timeouts. UUID casing is normalized. The key is scoped to the deployment and operation (`decision_docx` or `law_pdf`); JSON and multipart are equivalent transports when their normalized fields match. This deliberately breaks unkeyed upload callers. Authentication/caller namespaces remain H01: no client-supplied user ID, IP or arbitrary tenant header is treated as authenticated identity. These receipts do not establish access control.

A receipt reserves one document ID and one R2 key. Its fingerprint covers source SHA-256, file type, jurisdiction, title, citation, date, filename/MIME, vector request and explicit predecessor. Reusing a key with changed fields returns 409. Successful 201 responses are immutable ingestion snapshots: later approval, reviewer edits, rejection or vector progress do not rewrite the result. Use document/job APIs for current state. `vectorJobStatus: queued` means a durable verified outbox, not acknowledged Queue delivery or completed embeddings. Scheduled recovery handles failed dispatch.

An active retry returns 202 with `Retry-After`, `Location`, reserved identity and status. Poll `GET /ingest/requests/{ingestionRequestId}` or, after losing the entire response, `GET /ingest/requests/{original-UUID}?operation=decision_docx` (or `law_pdf`). A missing receipt returns 404. Polling does not mutate or restart work. States are `processing`, `retryable`, `complete` and `conflict`; `complete` includes the original result. Retry an expired/`retryable` attempt with the same upload and key. An active lease lasts three minutes, deliberately longer than routine ingestion; invalid/expired lease times permit recovery. Polling an expired processing lease still reports persisted processing until the next upload retry claims it.

Every ingestion mutation/batch includes an atomic owner/expiry check. A new owner can discard only unedited `preparing` rows at document revision 1 and rebuild from the same reserved source identity. A delayed old owner cannot publish, compensate or overwrite the newer database work. Publication, complete receipt, source lineage and verified vector outbox commit together. Completeness checks are inside that transaction; a lost acknowledgment is resolved by reading the receipt. An unfinished row edited outside the ingestion workflow is preserved with a conflict for manual reconciliation.

Reserved R2 objects are never deleted by delayed compensation. All retries for a receipt have the same verified byte fingerprint and deterministic object key, so a late upload can only write identical source bytes. A failed import can retain at most its reserved source object; it cannot become searchable or dispatchable. Retain these objects/receipts for reviewed recovery. Do not configure automatic R2 deletion by age without considering active/failed receipts and matching backups. Receipt deletion would remove the retry guarantee. There is no automatic retention cleanup in this change.

## Identical files and intentional revisions

A new key is an explicit new legal-record operation, even if citation, title or bytes match. The response reports verified historical upload matches (count plus at most ten document IDs) through the indexed SHA-256 lineage table. It does **not** merge records by title/citation or claim two legal records are equivalent. Distinct records may deliberately contain identical source bytes. Changed filename/metadata also changes the fingerprint; use the original request for retries. Existing duplicates remain untouched for separate domain-reviewed reconciliation.

To upload an amended source as the next revision of an existing record, use a **new** key and include:

```json
{"revisionOf":{"documentId":"doc_previous","expectedRevision":3}}
```

`expectedRevision` is the predecessor's current document revision from the reviewer detail endpoint, not the new source-revision ordinal. Multipart sends `revisionOf` as a JSON object string. Type and jurisdiction must remain the same. The predecessor must be the latest source revision; competing amendments, missing/stale predecessors or edits during extraction fail without committing another lineage entry. A conflicting request key remains a conflict; review the current record and use a fresh key. Failed preparation may remain retained for reconciliation.

`sourceIdentity` distinguishes immutable logical `recordId`, monotonic `sourceRevision`, predecessor and verified original upload hash from mutable reviewer/text-generation revisions. Extraction failure produces a replayable `needs_review` result without artifacts/vectors. Decision revisions pass the same human QC/approval gates as new decisions; an approved predecessor stays current until the successor is published. Law revisions follow the existing provisional law publication policy and do not gain human approval. Publication advances the logical source head atomically, excludes the older copy from public retrieval/source/assistant scope, and invalidates reviewer/vector/snapshot state. Rejecting/deleting/withdrawing the successor does not silently revive the older source. Review/archival source access remains separate.

The original receipt and source lineage describe the upload. Later retained generation restoration can change the document's active source/text; it does not rewrite the historical upload hash. No legal inference that an amended decision supersedes another is made from a shared citation. The operator must explicitly choose `revisionOf` and review applicability.

## Clients, rollout and rollback

The markdown/pilot importers and demo seeder derive stable keys from target origin, operation, canonical fields and source bytes. Rerunning an unchanged import after process/network failure converges. A 202 is reported as pending, not a successful completed import. Citation-only skipping is now opt-in (`*_SKIP_EXISTING_CITATIONS=1`), since it can hide amended sources. For an intentional distinct record with identical fields, use an explicit independently persisted UUID through the ingestion API. Importers do not infer revision relationships or automatically delete duplicates.

Apply migration 0032 and verify the updated M20 contract (32–32) before releasing the writer. The migration assigns each existing document its own legacy logical record, without changing source, approval or revision and without trusting declared old metadata hashes. No existing objects or duplicates are deleted. Rehearse a populated migration, repeated and concurrent uploads, R2/DB failure, commit acknowledgment loss, edited predecessor, Queue recovery and historical source exclusion in isolated preview.

**High change risk:** all upload clients must retain/reuse keys. After publishing source revisions, an older reader/writer that lacks logical-head filtering could expose multiple historical copies or bypass the protocol. Disable upload, approval, restore and other publication writes before rollback, and retain receipt/lineage/head tables plus the matching D1/R2 snapshot. Prefer a forward repair; do not erase receipt history or reset source heads to make an old release appear compatible. Authentication, reviewed duplicate reconciliation, real legal supersession decisions and production release remain outside this local implementation.
