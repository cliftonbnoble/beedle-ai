# Assistant history and input limits (M15)

The displayed/stored conversation is separate from the request context. The client sends a copy selected by the shared `assistantContextWindow` helper; the server applies the same helper before building its model context. No message is deleted from the conversation by this selection.

`assistantContextLimits` defines a 20-message transport ceiling, eight recent model-context messages, 12,000 characters per message, a 24,000-character combined history window, and 2,000 characters for retrieval query text. Character limits use JavaScript UTF-16 units to agree with Zod/client checks; they are not an exact model-token count or a billing estimate. Provider-specific context capacity and generation quality still need preview validation. The current question appears once in the model payload, with selected previous messages in the conversation data, so it is not charged twice against the stated history text budget.

Selection walks backward through nonempty, nonpending messages and retains a contiguous recent suffix that fits the message/count budgets. Prior oversize legacy messages are shortened only in the outgoing copy, without splitting a valid surrogate pair at the boundary. The current user question is validated first and is always retained in full within its 12,000-character limit. Original newlines remain in model question/history text. Requests must end with a user question containing at least three Unicode letters/numbers; empty/whitespace/punctuation-only/too-short and overlong questions fail with 400 before search/provider work. Prior short messages can still be context. The UI uses the same validation, shows its limit/count, disables invalid submissions, and the Enter handler validates before adding a pending message.

A conversation can continue beyond 30 exchanges because each outgoing request contains only its recent context. The 20-message transport ceiling remains deliberate for API consumers; clients should select their window before posting instead of submitting an unbounded archive. Schema/body/work limits remain enforced. Older request bodies with no final user question must migrate. The UI displays an earlier-context notice when messages have been omitted/shortened; no automatic summary is invented. Restate older facts when they matter. Losing an antecedent outside the retained window is an explicit limitation; M16 owns follow-up resolution and selected-case scope.

Retrieval compacts whitespace and uses the existing issue-prefix heuristic, then bounds long text to the first roughly 70% and last roughly 30% of its 2,000-character query allowance. Both ends of the question are retained to reduce the chance of losing a trailing issue. Surrogate boundaries are preserved. If extreme punctuation would exclude all search terms, a bounded lexical-word copy is used. This is a deterministic lossy retrieval representation, not a semantic summary or exhaustive search of every fact. Add a specific issue when the derived query lacks searchable content. Search work-budget rejection can still ask the user to narrow an expensive query.

`retrievalContext` exposes the effective query, whether it was shortened, retained message/character counts and how many submitted messages the server omitted. Those counts refer to the submitted context, not the unseen full client archive. The UI shows a shortened-search disclosure even for a no-evidence answer. It stores the effective query for source links, and the decision-link builder also bounds legacy query strings, so a 12,000-character chat question cannot become an invalid oversized reader search parameter. Full user text remains visible in its own chat message and is preserved for generation. Status/error messages carry current no-evidence metadata rather than being mislabeled as a checked factual answer or a legacy source assessment.

## Verification and rollout

Behavioral coverage includes 35 exchanges/70 retained history messages, bounded requests on every turn, context character/count seams, pending/blank artifacts, legacy oversize history without mutation, Unicode boundaries, full 12,000-character model input with a valid bounded search request, and early rejection with zero database work. Actual local workerd/D1/R2 completed 31 exchanges with eight-message request windows, skipped generation for empty retrieval and accepted a 12,000-character question with a 2,000-character retrieval query. Synthetic providers only; no paid calls.

Isolated Chrome loaded a 60-message conversation, completed its next exchange, and kept all 62 messages/oldest content visible while sending eight messages. The composer showed and blocked a 12,001-character question without adding a message. A 12,000-character question submitted successfully, kept the full user text, displayed the shortened-query notice and produced original-decision links below the 2,000-character query cap. API behavior/source and web checks, workspace types and a Worker dry run accompany the change.

Deploy API/web/shared contracts together. No migration or stored-history rewrite is required. Keep complete history when rolling back; prefer a forward context-window correction to restoring whole-history requests or removing request limits. This does not repair the existing live-state/storage coupling, cross-tab conflicts or quota handling; M17 owns that work. H01 authentication and Low findings remain out of scope.
