# Runtime contracts and generated types

L02 makes the configured Worker bindings and the external/serialized payload boundaries checkable. There is no database migration or authentication implementation in this change.

## Bindings and runtime declarations

`apps/api/src/worker-configuration.d.ts` is generated by the repository's pinned Wrangler/workerd version using the actual compatibility date and flags. It supplies D1, R2, rate-limit, AI, Queue and runtime declarations. The API no longer mixes handwritten binding declarations, `@cloudflare/workers-types` and the browser Web Worker ambient library. Cloudflare's [TypeScript guidance](https://developers.cloudflare.com/workers/languages/typescript/) describes configuration-derived types.

`Env` extends the generated binding contract. Its explicit overlay contains request-owned telemetry/readiness/work-budget state, deployment-injected release values, the optional LLM credential, the deployment-environment discriminator and the Queue message type. It does not redefine resource bindings. Removing or renaming `DB` therefore breaks application typechecking, as a negative compiler fixture verifies.

From the repository root:

```sh
pnpm --filter @beedle/api types:generate
pnpm --filter @beedle/api types:check
pnpm typecheck
pnpm --filter @beedle/api test:integration:types
```

Generation writes a declaration file only. It uses a private temporary flat config, explicit paths, empty dotenv files and a minimal child environment. Local `.dev.vars`, account credentials and deployment secrets are excluded. Generated module references are relative; temporary files are unique, excluded from TypeScript and ignored by Git. `types:check` regenerates for comparison without replacing the checked-in file. Runtime generation starts local workerd and needs loopback permission; it does not deploy or inspect Cloudflare resources.

Run generation after changing the Wrangler config, compatibility settings or pinned Wrangler dependency. The freshness check is mandatory in the reusable CI gate and therefore before deployments. Config resource identity and release readiness are still enforced by M20; a type check cannot establish that a remote resource was provisioned correctly.

The generated runtime requires explicit `TextDecoder` options. Existing fatal UTF-8 decoders now specify `ignoreBOM:false`, preserving their previous default behavior.

## Runtime payload validation

| Boundary | Validation and failure behavior |
| --- | --- |
| Worker AI embeddings | Treat the binding result as `unknown`; check capacity before traversing arrays, then validate batch count, optional shape, dimensions and finite numeric vectors. Fetch response chunks are checked as bytes; invalid UTF-8/chunks cancel the producer and report `invalid_response`. A valid vector in a partial batch remains usable; invalid vectors report `invalid_response`. The SDK model-key assertion is limited to trusted deployment configuration, not provider payloads. |
| Activation plans/staging | Public DTOs retain the strict activation schemas. Stored plans and staged chunks pass those schemas before digest comparison or publication. Corrupt stored JSON produces a controlled conflict without further embedding/publication. |
| Durable maintenance | Validate the frozen backfill/activation plan, source kind, generation, reference arrays and progress. Validate every selected vector item before starting any provider work in that step. Invalid saved state fails/holds the job; completed checkpoints remain intact. |
| Ingestion receipt replay | `packages/shared/src/ingestion-contract.ts` defines the current V1 result contract and inferred result type. Both status polling and all replay/lost-ack paths validate it and correlate document/request IDs and immutable source identity with the reservation. Malformed, unsafe-number or mismatched results cannot be returned or cause ingestion to run again. |
| Stored JSON helper | Enforce a finite ceiling of 2,097,152 UTF-16 code units, parse to `unknown`, then validate the required schema. Return a generic 409 for inconsistent stored state without echoing source values. |

V1 names the existing receipt structure; it introduces no new wire field or fingerprint normalization. Completed valid M22 receipts retain their data and source identity. A future result-contract change must preserve replay compatibility explicitly. Do not “repair” a corrupt completed receipt by deleting it or choosing a new UUID: recover the matching receipt/source evidence from a consistent backup. Unknown/overbound legacy maintenance payloads may now be held and require a fresh reviewed plan. No stored approval, governing-law binding or actor attribution is invented.

Binding method proxies forward opaque members as `unknown`, preserve their receiver and validate selected row shape rather than hiding SDK values behind `any` or double assertions. The router carries explicit request, environment and response generics and satisfies the generated Worker handler contract.

## Focused async/type lint gate

```sh
pnpm --filter @beedle/api lint
pnpm --filter @beedle/api test:contracts
```

The current ESLint/TypeScript plugin baseline covers ingress, provider operations, activation, embeddings, ingestion receipts and durable maintenance. It checks floating/misused promises, awaited values, explicit `any`, unsafe assignment/arguments/return/calls/member access and double assertions. Payload modules also reject unsafe narrowing assertions; the single deployment-model SDK bridge is explicitly documented. It does not impose formatting or claim the entire historical codebase has been linted. Expand the explicit boundary list when changing another boundary.

Awaited work, aggregated promises and `ctx.waitUntil` are accepted; a rejected cancellation promise is explicitly observed while keeping the existing request deadline. Negative/positive fixtures exercise the actual linter, and a compiler fixture renames the generated D1 binding in memory to prove the build fails. See the primary [typed-linting documentation](https://typescript-eslint.io/getting-started/typed-linting/) and [floating-promise rule](https://typescript-eslint.io/rules/no-floating-promises/).

## Verification and rollout

API behavior, source/queryability, utility/web and tooling checks, workspace/integration types, generated-type freshness, the actual Pages adapter build and native Worker/D1/R2/Queue/recovery fixtures cover the change. Native fixture setup timed out during a concurrent adapter build; the separate native run passed all 16 checks. CI already runs native verification before the adapter build. Keep installs/builds separate when reproducing this on a constrained workstation.

There is no production/provider certification in these tests. Rehearse actual provider response shape and representative saved jobs/receipts before deployment. Malformed stored payloads now hold with a controlled conflict; they previously escaped static checks or failed incidentally. Use the existing release/rollback gate, preserve completed receipts and investigate held state. Authentication remains deferred.
