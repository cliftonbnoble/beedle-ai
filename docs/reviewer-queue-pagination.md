# Reviewer queue materialization and pagination (M13)

Migration 0030 adds a disposable reviewer policy index. Listing no longer refines an arbitrary 2,000/4,000-row candidate pool in JavaScript. Every document is evaluated by the same policy functions used by document detail; the materializer aggregates reference/link counts for up to 25 explicit IDs at once. List SQL filters and sorts the stored policy output, including exact readiness, blockers, triage buckets, risk, effort, runtime disposition and citation families. The approximate SQL copies of reviewer policy were removed.

## Read and cursor contract

`GET /admin/ingestion/documents` defaults to 50 rows and caps each page at 100. Existing limits up to 2,000 are accepted and clamped; callers must follow `nextCursor`. All existing sort modes have deterministic ID tie breaks. Title and tie ordering use SQLite binary comparison rather than locale-dependent JavaScript ordering. Cursor requests may change page size, while retaining their other filters/sort. Query matching still uses SQL LIKE on title, citation and case number.

`summary` contains exact totals for the **entire matching queue**, with `scope: matching_queue` and `countKind: exact`. `pageSummary.total` and `page.count` are page counts. `page.complete` means the current position has no following page. The old derived-candidate-cap fields are retired. Totals and some derived sorts still require SQL aggregation/sorting over the matching materialized set; this is not constant-time counting or a universal indexed-sort claim. Common creation/title/readiness/effort/group/type/risk/fixture paths have indexes. Measure larger representative corpora before rollout.

A queue epoch advances for document, reference-link, reference-issue and active-catalog changes. A cursor binds its position to that epoch, normalized filters and policy version. Reads check readiness/epoch again after counts and page selection. Changed queues/filters return 409 and require restarting. No pages are spliced across versions. Cursors encode bound keyset positions; they are not authorization credentials or a private-data access mechanism. H01 remains responsible for authenticated principal/tenant scope; introduce that scope before exposing permission-dependent materialized rows or groups.

Rows contain `triageGroupKey` and `peerCount`, not arrays of every peer. Group counts are maintained atomically when an indexed row changes groups or is deleted. Their scope is **all documents in the reviewer index**, independent of current list filters. They describe a shared triage signature, not permission to approve or bulk-correct those documents. `GET /admin/ingestion/reviewer-peers?groupKey=...&documentId=...` loads at most 100 peer IDs, excludes the supplied document, and returns its own cursor/exact total. Omit `documentId` to enumerate all group members. The UI labels the global scope and loads peers only on demand.

The UI keeps one 50-row page, supports previous/next/restart, and labels queue versus page counts. Latest-request fences cover list, index-refresh and peer reads. Queue changes clear the stale page/peer panel and show the restart guidance. There is no ever-growing list to virtualize. API list/peer responses are private/no-store.

## Bounded build and freshness

- `GET /admin/reviewer-index` is read-only status: phase, high-water keyset cursor, source/indexed counts, dirty count, catalog/policy versions and readiness.
- `POST /admin/reviewer-index/step` with `{}` processes at most 25 documents and does no provider work. Repeat until `ready: true`; the state is durable across Worker restarts. Observe the existing admin-write quota/retry-after rather than flooding the endpoint.
- A 60-second lease serializes builders. Each checkpoint atomically checks ownership, unexpired lease, current catalog and every captured source version before storing rows, group counts, dirty clears and progress. Source changes roll the batch back. A checkpoint token reconciles a lost acknowledgment.
- An initial or changed-policy/catalog build walks a finite captured upper document ID. Inserts/edits below that cursor remain in the indexed dirty queue and run after the finite pass. New IDs above its upper bound also enter the dirty queue. Deletions cascade derived rows and group counts.
- Dirty tracking includes review changes that do not advance the evidence revision (for example, approval publication), as well as reference changes while ingestion is preparing. Counts and current catalog/policy must agree before listing is ready. Missing derived rows trigger a bounded rebuild rather than an empty complete result.
- Scheduled execution advances one checkpoint. Successful metadata, approval, rejection and reprocess routes also schedule one checkpoint. Other imports/catalog changes are picked up by the scheduled or explicit builder. Pure search/index dry runs do not schedule unrelated reviewer writes. Large initial builds must finish during release preparation; a cron-only first build can take many runs.

Listings return 503 with refresh guidance while any required policy state is stale. This deliberately favors a complete current queue over silently hiding dirty or not-yet-indexed documents. Under sustained corpus writes the queue can remain held; schedule sufficient maintenance capacity or use an explicitly designed snapshot generation if the workload later needs concurrent old-generation browsing. Policy input and stored output each have a 64 KiB per-row cap; the source query projects only the taxonomy/filename metadata actually used. A step also caps reference detail at 2,000 rows and 1 MiB before loading those details. Exceeding these bounds holds materialization for source-data inspection rather than returning an unbounded response. General metadata/reference input bounds remain M25.

Policy output changes require incrementing `REVIEWER_POLICY_VERSION`; the approval policy version is included automatically. The current catalog version also forces rebuilding. The cache is not authoritative evidence. Metadata saves, approval and rejection continue using their evidence revision guards independently of cached queue readiness.

## Maintained consumers and release

Reviewer exports collect bounded pages up to their existing 2,000-document export limit and fail on a version conflict instead of producing a mixed packet. Maintained operator/report scripts use the read-only pagination helper, preserving their requested collection limits up to 2,000. The helper exposes `collection.complete`/`nextCursor`, refuses mixed epochs or repeated IDs and never automatically changes server state. Larger workflows can traverse cursors explicitly or collect smaller exported batches. Old scripts that assumed one response contained hundreds/thousands of rows must migrate. The unresolved-triage report also uses compact API group metadata.

Apply/rehearse migration 0030 on a backed-up preview database, deploy coordinated readers/writers, finish bounded reviewer-index steps, then enable queue use. No source text or document approval is rewritten by this migration/build. Test source-trigger overhead, initial build duration/storage, aggregate rows read and dirty-queue drain rate on a representative corpus. The 77-document local D1 fixture's seven-row listing used five statements, 1,395 reported rows read, zero rows written and zero DDL; this illustrates the remaining exact-total aggregation cost, not a production SLO. The 4,207-row Node/SQLite fixture traversed 44 pages without duplication or truncation, with a roughly 263 KB 100-row response and 64–110 MiB process heap observed across runs of that fixture (including test data and garbage-collection timing). These are local measurements, not Worker heap or production latency guarantees.

Rollback should preserve the queue tables/triggers and guarded metadata APIs. Prefer a forward cache rebuild/version bump to restoring the capped legacy reader. To deliberately discard derived state, first hold reviewer traffic and stop active builders, retain a consistent database backup, remove only reviewer state/group rows in a guarded maintenance transaction, and resume bounded steps; source/indexed count checks keep incomplete state held. Do not restore reviewer controls independently of source/reference data. M26 owns whole-database recovery and post-restore cache regeneration. Authentication and Low findings remain out of scope.
