# Versioned vector lifecycle

M04 adds migration `0022_vector_generations.sql`. It does not change, overwrite or delete the existing provider namespace during implementation. No paid AI/Vectorize calls or production migrations/deployments were performed.

For the current product-search filter rollout, also follow [M05 semantic filtering](vector-filtering.md), including its complete index manifest and separate readiness flag.

## Identity and receipts

An embedding profile records the model, exact dimension count and extraction/query/chunking pipeline versions. Its namespace is `<environment-base>-g<profile hash prefix>`. Changing the model, dimensions or either chunking pipeline changes this namespace. `AI_EMBEDDING_DIMENSIONS` is explicit in deployment configuration (768 for the existing BGE base model). Source entries additionally retain the observed concrete parser, document/text or activation generation, captured source SHA-256, chunk text/digest and original document revision. Unknown historical parser provenance is labelled unverified.

A logical entry identifies that complete immutable input. A physical provider ID identifies one submission incarnation and fits the provider's 64-byte limit. Physical IDs are not reused after uncertain submission or deletion. A late initial upsert or asynchronous deletion therefore cannot overwrite a replacement incarnation. A partial unique index, embedding leases and submission guards reconcile competing source jobs. Successful embeddings are cached before submission; document jobs batch up to four model inputs and sixteen vector writes, clipped to the configured shared budget units. Finite values and exact dimensions are checked before writes and again when verifying stored vectors. Cached embeddings are reused after provider write failure. Shared quotas still charge every attempted text/vector operation conservatively.

Receipt states distinguish prepared values, in-flight submission, acknowledged submission, verified provider visibility, uncertain outcome, deletion intent and confirmed absence. Unknown initial acknowledgements create a fresh physical incarnation on retry while reusing cached values. A crash during submission is held briefly before being treated as uncertain. No unverified/uncertain entry is eligible for semantic results. Job completion records its embedding profile; a changed profile requires a new backfill rather than silently continuing a mixed-model job. Existing v2 activation plans with vector writes must be prepared again to capture the profile in their signed digest. Historical published plans remain readable/replayable and retained rollback evidence is preserved.

## Retirement and query consistency

Source/publication changes advance a durable document revision signal and a corpus epoch. Reconciliation is checkpointed independently for each profile, so a shadow profile does not falsely mark a baseline synchronized. It updates at most four documents and sixteen metadata records per document in a delivery; missing current incarnations can be rebuilt in a separate bounded work unit. Post-mutation, queue and scheduled entry points advance this work.

The new provider namespace requires a boolean metadata index named `live`, created **before** upserting its vectors. Queries always specify the profile namespace and `live: true` before top-K. They never fall back to an unscoped namespace. D1 maps provider identities back to current chunk identities and remains authoritative for publication. A dirty profile or a changed corpus epoch during a query causes explicit semantic degradation; lexical retrieval remains available. This avoids treating a set filled with obsolete generations as complete current recall. Other accepted query filters are addressed in M05.

Metadata promotion/retirement is serialized by a durable profile/document lease. A known mutation acknowledgement with delayed visibility is observed before another metadata write can proceed. An **unknown metadata acknowledgement** holds that synchronization and semantic readiness, because racing an uncertain old write with a new promotion could put an obsolete generation back into recall. Inspection reports held synchronizations. The explicit `recoverUncertain` operation is for an operator who has verified that the provider mutation queue has settled; using it prematurely can reintroduce that race. Automatic retries do not guess. A stale owner with a recorded mutation intent also enters this held state after its lease expires.

## Operations

- `GET /admin/vector-generations` reports the configured profile/namespace, synchronization readiness, held work, D1 source coverage and receipt counts. Readiness means consistent known entries; it does **not** imply complete embedding coverage or independently validated relevance.
- `POST /admin/vector-generations/sync` accepts `{}` or an optional `documentId` and advances one bounded synchronization delivery. `recoverUncertain: true` explicitly releases an expired/ownerless held mutation after the operator precondition above.
- `POST /admin/vector-generations/reconcile` accepts an optional `after` physical ID and checks at most 32 verified records against provider IDs, namespace, digest, dimension/finite values and live state. Continue with `providerProbe.nextAfter` to inspect all pages. It reports missing/mismatched provider rows without silently recreating an entire index. Quarantine a discrepant profile, inspect provider mutations and rebuild/validate a replacement profile before promotion.
- `POST /admin/vector-generations/cleanup` defaults to `{ "dryRun": true }`. Actual cleanup claims at most 32 owned obsolete physical IDs, submits `deleteByIds`, and records deletion only after absence is observed. Deletion intent is durable and retried on subsequent deliveries. Fresh incarnations use different IDs, so delayed deletion does not race restored content.

Obsolete verified vectors and uncertain initial submissions have a **30-day** retention interval. Dirty/current entries are protected; verified vectors belonging to published activation plans remain protected as rollback evidence. Rolled-back obsolete activation rows and replaced/rejected document vectors become eligible after retention and synchronization. Restoring an eligible document rebuilds a fresh incarnation from the retained source when necessary. Cleanup charges the vector-write work budget for metadata updates/deletions as well as upserts. It does not delete retained D1 text/source generations or legal evidence.

The old unversioned namespace is excluded from new recall and retained for rollback. Its historical vectors predate these receipts; do not invent model/source provenance for them. Inventory and verify that namespace through the provider's management tooling before a separate, explicitly targeted legacy purge after the rollback window. The runtime collector deletes only registered application-owned physical IDs.

## Shadow evaluation and rollout

1. Apply migration 0022 to isolated preview, configure exact dimensions, and create its `live` metadata index. Keep production `VECTOR_LIFECYCLE_READY=false` during preparation. This repository intentionally leaves readiness false in saved deployment environments until their external index prerequisites are completed.
2. Use the bounded M03 backfill jobs to build the profile namespace. Advance synchronization, reconcile expected source coverage, and check every provider page. Resolve held/missing/mismatched rows. Increasing configuration readiness is not a substitute for those checks.
3. Compare a retained baseline and candidate preview API with `scripts/vector-generation-shadow.mjs`. Set explicit `VECTOR_SHADOW_BASELINE_URL`, `VECTOR_SHADOW_CANDIDATE_URL`, `VECTOR_SHADOW_QUERIES_FILE` (a JSON array of up to 20 queries) and a new `VECTOR_SHADOW_REPORT_FILE`. It records profile/coverage, latency and result identities/overlap, without excerpts. It does not mutate either API's corpus or claim overlap is relevance. Queries can incur the configured embedding budget.
4. Review independent relevance judgments and latency before enabling `VECTOR_LIFECYCLE_READY=true` for that configured profile. Preserve the prior deployment/index/namespace and source snapshots for rollback. Different dimensions may require a separately provisioned Vectorize index/binding, not just another namespace; verify the provider index dimension before any model migration.
5. Roll back code/profile configuration and binding together if needed. Do not drop receipt tables or delete old namespaces during rollback. Old code uses the retained old namespace; a retained M04 profile can be resynchronized and queried in its own embedding space.

These are release prerequisites, not production actions performed in this task. Authentication/actor authorization remain H01.

## Verification

Behavior tests cover model/profile isolation, exact dimensions, finite values, source versions, batched/cached work, long-document checkpoints, partial/unknown acknowledgements, concurrent embedding and metadata leases, asynchronous visibility, rejection, restoration with fresh IDs, corpus changes during queries, rollback protection, retention and provider reconciliation. The D1 adapter now models trigger-inclusive change counts; affected document mutations use returned target IDs, so lifecycle triggers cannot falsely report approval conflicts or inflate publication counts.

An actual isolated workerd/D1/R2 run approved a synthetic decision, built and verified four versioned vectors, synchronized and reconciled their namespace/metadata, retired all four after rejection, and confirmed retention prevented immediate deletion. Providers were in-process synthetic implementations; production provider timing, index metadata configuration, coverage and relevance remain preview rollout checks.
