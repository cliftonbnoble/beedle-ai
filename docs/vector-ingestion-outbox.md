# Verified ingestion outbox (H15)

Apply migration `0018_vector_job_outbox.sql` with this application version, after H14. Initial ingestion has no vector job while it is preparing text. After all artifact batches and the R2 write complete, it reads the persisted chunks, checks their expected count and computes a SHA-256 manifest over ordered IDs, text, section labels, paragraph/citation anchors and chunk order. It reads back and verifies the source bytes against the extraction hash. The final D1 transaction publishes the complete document and inserts its verified outbox row together. Queue delivery is attempted only afterward.

H12 reprocess/restore uses the same outbox writer. It hashes the complete staged chunk generation before the guarded projection transaction, then records the newly published generation/source and expected manifest in that transaction. The shared writer resets lease/progress only for this explicit generation replacement.

Each outbox records readiness time, preparation revision, text generation, immutable source key/hash, expected chunk count and ordered chunk digest. The preparation revision is provenance, not approval: later reviewer metadata/confirmation edits may advance the document revision while the exact source/text generation remains unchanged. H14 captures the current revision on each claim and fences changes during computation. The consumer requires the current text generation and source identity, a ready document, and an exact chunk/source manifest match before embedding and again before finishing a delivery. A superseded generation cannot claim. Missing or changed evidence fails the job for explicit reprocessing instead of consuming repeated provider attempts.

The sweeper, direct enqueue helper and consumer all require a verified outbox readiness marker. Queue messages alone cannot create work or promote a partially stored document. A failed queue send leaves a ready durable row for the scheduled sweep. Compensation conditionally deletes only the untouched preparing import; it never deletes a ready document or concurrently edited revision. If the final commit acknowledgment is lost, the source/document/outbox receipt is inspected before reporting success. If the database outcome cannot be inspected, artifacts remain preserved and preparation state cannot dispatch.

## Rollout and recovery

Pause/drain old consumers and complete unfinished old ingestions before migration. The old application must not keep writing jobs without manifests. Migration 0018 holds old queued/processing jobs as failed with an explicit legacy-manifest reason. It preserves completed/failed history and does not fabricate hashes from possibly incomplete old imports. Inventory those rows with `GET /admin/vector-jobs`; `outboxReadyAt`, `preparedRevision` and `expectedChunkCount` identify the new contract. Reprocess selected legacy documents through H12, inspect the new extraction, and reconfirm/reapprove as required. Do not bulk backfill readiness markers or reset failure counters to bypass verification.

After an ambiguous ingestion outcome, inspect the document and outbox before retrying a whole upload. A verified ready row needs only queue recovery. A retained preparing row needs diagnosis and an explicit reprocess/review; it is not automatically promoted by a sweep. Preserve the original source and staged rows until the failure is understood. Provider vector garbage collection and a general ingestion idempotency-key API remain separate scope.

Automated tests interleave sweeps/consumers after every text batch, inject artifact/source/publication failures, lose final commit acknowledgments, make outcome inspection fail, corrupt source/chunk manifests, exhaust dispatch availability and migrate old job states. Isolated workerd/D1/R2 testing verifies read-back source hashing, atomic outbox publication, one concurrent claim, completion/replay and operator visibility for 24 chunks. AI/Vectorize are instrumented locally; no production migration or provider writes were performed.
