# Indexed lexical retrieval and request budgets (M06)

Text recall has independent body and title/citation/author channels. Migration 0024 adds source-backed FTS5 trigram indexes, integer identity maps and transactional insert/update/delete triggers. The index stores token postings; external-content views read the authoritative text. Substrings inside words (for example `rent` inside `parent`) remain reachable, as do metadata-only hits when the body phrase index returns zero. Existing structured/citation filters remain separate and apply before candidate selection. D1 hydration/publication checks remain authoritative.

Each substring recall call takes at most 1,600 eligible body identities and 200 eligible metadata documents, with two representative chunks per metadata document. Stable rowid order bounds recall before weighted ranking. Ranking uses the existing field weights over these candidates, rather than repeated `instr()` expressions over the corpus. The phrase channel remains independent. Keyword and issue document fallbacks use the same indexed kernel; scoped lexical/phrase searches bind a JSON ID set rather than serial four-document batches. This deliberately bounds candidate recall, **not** an assertion of exhaustive matching or exact corpus totals. M08 addresses result sessions/count semantics.

FTS5 trigram MATCH supports terms of three or more Unicode characters. A fallback containing no indexable term returns a safe 400 asking for three characters or structured filters; it never launches an arbitrary two-character corpus substring scan. In a mixed OR vocabulary, only indexable terms feed this channel. Phrase/token matching has its existing separate semantics. This contract and broad-query candidate truncation require product/relevance review before rollout.

One `SearchWorkBudget` follows all search passes in an HTTP search or research request. Limits: 25 seconds elapsed, 96 SQL statements, 12,000 returned rows total, 2,500 per query, 16 MiB returned JSON, two million reported D1 rows read, eight embedding texts, 16 vector queries, 30,000 scoring operations and eight pipeline passes. The full-pipeline retry is removed; zero-hit correction can consume one additional pass under the same budget. Per-provider timeouts remain shorter when appropriate. Started asynchronous work is observed; request cancellation/deadline propagates to providers that support it. No mutable authorization/publication check is cached.

A sticky budget failure becomes a safe 503 asking for a narrower query. A caught stage error cannot reset it or present exhaustion as a genuine zero hit. Debug responses report numeric usage without SQL. D1 does not expose statement cancellation: elapsed/rows-read guards bound further work and response waiting, **not** the cost of an already-running query. Indexed plans, D1 platform limits and load testing are still required. The configured limits are initial safeguards, not measured production SLOs. M09 separately removes legacy cold-start DDL.

## Upgrade and rollback

1. Apply additive migration 0024 in a disposable/preview environment first. Fresh empty databases are ready; populated upgrades start unready. Existing writes keep both new channels current while the old index/readers remain available.
2. Inspect `GET /admin/search-index`. Repeated `POST /admin/search-index/step` with `{}` visits at most 100 source identities per call, freezes the selected IDs, and atomically writes missing postings plus its cursor under a 60-second owner lease. Replay skips already indexed identities. A failed transaction does not advance the cursor; expired leases are reclaimable. The final transition verifies all three source populations are mapped/indexed. Polling itself does not run coverage scans.
3. Complete the build before exposing new readers. New readers return 503 while it is unready. A populated production switch therefore requires a coordinated maintenance window or an operator-controlled staging builder against the intended database, followed by a verified ready state; do not switch and hope lazy request repair finishes it. No production migration/backfill was executed for this work.
4. Compare an independently judged real-corpus holdout against the prior revision in preview: common/rare/zero-hit, inside-word, metadata-only, quoted, short inputs, all structured filters and high document/chunk counts. Record cold and warm p50/p95/p99, D1 rows read, statement counts, recall/NDCG and candidate-cap effects. Measure trigram index size and ingest/update/delete cost as well. Change caps only with that evidence. M19 provides the broader holdout workflow.
5. Keep the previous code and old `search_chunks_fts` index for rollback. Roll back code while retaining additive schema and its maintenance triggers; dropping a new table under an active writer is unsafe. Investigate and resume an incomplete build instead of marking it ready manually. Corruption/restore reconciliation is extended under M10.

## Local evidence

Behavioral tests execute the real SQL/services against SQLite: inside-word and metadata recall, combined filters, whole-word rejection, zero hits, explicit short-input refusal, MATCH-constrained query plans, populated/replayed builds, live insert/edit during the build, owner conflicts, transaction failure/recovery, deadlines/cancellation, row/query/CPU limits, shared sticky budgets and no pipeline restart. A 250-document synthetic benchmark covers common/rare/zero/metadata classes; its measurements are diagnostic, not release thresholds.

Disposable workerd/D1/R2 executed the actual migration, upload/approval and product `/search`. Metadata-only title retrieval passed; existing scoped vector behavior still passed with 120 higher-scoring distractors. Fifteen tiny-corpus cold/warm debug calls used 3–5 statements and 9–47 reported rows read, taking 2–14 ms locally. No paid providers or production resources were used. A real corpus and independently judged relevance/production latency remain explicit release gates.
