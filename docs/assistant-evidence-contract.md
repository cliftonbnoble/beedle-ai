# Assistant claims and prompt boundaries (M14)

Assistant responses now distinguish generated claims, exact quoted spans and the larger retrieved source set. Retrieval never establishes that a legal proposition is true or that a source entails it.

## Response and validation contract

New responses have `assessmentVersion: claims-1`. `claims` contains server-assigned claim IDs, text, an explicit `unverified` or `source_excerpt` status, review flags and passage-level evidence. Every evidence span identifies its current retrieved document/chunk/paragraph/citation anchor, quote, normalized excerpt and offsets. `occurrenceVerified: true` means only that `excerpt.slice(start,end)` equals the quote. Offsets are in the **normalized retrieved excerpt**, not the complete source document, PDF bytes or original paragraph.

The completion must return one strict JSON object with up to eight `{text,evidence:[{sourceId,quote}]}` claims. Claims are capped at 1,200 characters, with at most three quote references each; quotes are 20–1,200 characters. There is no separate free-form answer/summary that can bypass validation. The server constructs answer text and citation markers from accepted claims.

The current request's trusted/published retrieval results determine the passage-ID allowlist. The provider cannot supply document links or invent a new source. Checks reject unknown structured/inline source IDs, quotes absent from their identified normalized excerpt, unrelated sentence vocabulary, detected negation disagreement, unmatched numbers and provisions (including Rule Part identity). Unknown model fields, prose/Markdown wrappers, malformed JSON and truncated responses also fall back. These inexpensive checks are **conservative failure detectors**, not a semantic entailment verifier. They can miss subtle fabricated facts, attribution mistakes or legal distinctions, and can reject valid nuanced comparisons. All generated claims remain visibly unverified even after these checks; no confidence score or “verified support” label is inferred from lexical overlap.

`citations` includes only decisions actually referenced by accepted claim/excerpt spans. `retrievedSources` separately records all retrieved decisions; unused candidates are not attached as claim support. `retrievedCount` is the bounded retrieval count, not a corpus-wide case/outcome count. `evidenceStatus` distinguishes `unverified_claims`, `retrieved_excerpts` and `no_evidence`. `evidenceCapturedAt` and `evidenceCorpusRevision` identify the retrieved snapshot. A final budgeted corpus-revision fence returns 409 if the corpus changed while generating; the caller must retry against current evidence. Later edits can still change the original decision, so saved excerpts are historical and require rechecking.

A failed completion/check produces an explicit safe `fallbackReason` and deterministic source excerpts, labeled for relevance review. It does not present the rejected generated answer. Only excerpts actually shown become citations; other retrieved candidates remain separate. With no usable passage evidence, configured generation spends no provider request or compute reservation and returns a no-evidence answer. Unconfigured generation retains its explicit fallback. Existing provider deadlines, bounded body consumption, cancellation, output-token and aggregate cost limits remain in force.

Older responses default to `assessmentVersion: legacy-1`; stored messages without the new version display a legacy notice. Their historical answers/citation lists are not retroactively treated as checked claims. The UI stores the optional structured metadata, labels claim support as unverified, shows exact quoted spans/original-decision links and the evidence date, and has a distinct all-retrieved-sources panel. Plain text remains escaped by React. H01 identity scope and M17 general storage lifecycle/migration remain separate.

## Prompt roles

Both assistant and drafting calls send exactly one fixed system instruction message. Question, conversation (including prior assistant text), scope/index-code values, source titles/excerpts, findings, supplied law, style preferences and retrieval explanations are serialized as JSON in **user-role data**, never interpolated into a system message. Draft output retains H09's paragraph-level unverified/support diagnostics. The assistant accepts evidence only from the current retrieved set, regardless of prior chat claims.

JSON preserves structural message boundaries when data contains fake delimiters, quotation marks or role claims. It does **not** prove immunity to natural-language prompt injection. There are no new model tools or side effects. Source IDs/quotes and safe rendering add checks around the output; human legal review remains necessary. Source kind/section names come from the retrieved passage, so a generic matched passage is not relabeled as a conclusion of law merely because no authority passage was found.

## Verification, rollout and rollback

Behavioral checks cover fabricated structured/inline IDs and quotes, irrelevant attached sources/sentences, no-source generation, contradictory polarity, counts, wrong provisions/Rule Parts, exact span offsets, corpus changes during completion, and fake system/delimiter content in question/scope/history/source and drafting inputs. Actual workerd/D1/R2 used a strictly intercepted synthetic completion endpoint to verify successful structured output, rejection/fallback paths, zero provider calls on empty retrieval and fixed system/user roles. Isolated Chrome verified the separate 1-cited/2-retrieved panels, unverified claim/evidence date display, lazy quote/original-source details, fallback excerpts and legacy labeling. No actual provider charges, production writes or deployment occurred.

Deploy coordinated API/web changes. No migration is needed. Models/providers that fail the strict JSON/quote contract will fall back more often; keep the current cost/token limits and measure that rate in preview. Before deployment or loosening checks, evaluate independently human-reviewed examples for factual attribution, paraphrase entailment, contradictory cases, mixed claims, short excerpts, provisions/editions and abstention. M19 provides the evaluation workflow; no synthetic result here is a factual-accuracy or prompt-injection benchmark. Judge filters/follow-up resolution and message windows remain M15/M16; legal editions remain M18.

Prefer a forward correction. Preserve `claims-1` metadata and the legacy/unverified labels on rollback. Do not restore the prior behavior of labeling every retrieved document as answer support or putting user/source data into privileged roles. Existing saved messages continue to render, with explicit legacy provenance when the evidence contract is absent. If structured generation is problematic, retain the extractive path while keeping source distinctions and review labels.
