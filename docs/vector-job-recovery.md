# Vector job leases and recovery (H14)

Apply migration `0017_vector_job_leases.sql` together with the H14 consumer. Pause/drain the old consumer before switching application versions: it cannot honor new owner tokens. Existing queued messages without a generation ID still target `initial`; they cannot claim replacement generations. Existing completed/failed rows remain terminal. Legacy processing rows without a lease are treated as abandoned, and historical attempts conservatively consume the failure budget.

Each claim atomically assigns a random owner token, captures the current document revision/text generation and increases `attempts`. A valid owner renews its two-minute lease before every group of four embeddings and before each vector upsert. Progress, completion and failure updates require the owner token, generation and unexpired lease; progress/completion also require the claimed document revision still be current. A stale owner cannot alter replacement work. Document reprocessing creates a new generation with a fresh job budget and clears all old lease/progress fields.

Provider calls are bounded to 15 seconds. Started embeddings are awaited together before releasing ownership. A delivery processes at most 64 chunks, upserting groups of 16 and checkpointing the acknowledged offset after each group. Longer jobs return to the durable queue state and continue on a subsequent sweep. A response lost after upsert can repeat the same IDs; a response lost after database completion cannot reopen the job. Source chunk IDs remain generation-specific. Provider submission acknowledgment does not guarantee immediate query visibility; H13 activation separately verifies stored vectors before publishing its retrieval generation.

`attempts` counts actual claimed deliveries, including productive continuations. `failure_count` counts failed/abandoned claims and never resets merely because a new queue message was delivered. Five failures make a job terminal `failed`. Failures use exponential backoff starting at 60 seconds plus 0–29 seconds jitter. Lease recovery consumes one failure and applies the same backoff from the lease expiry; recent expirations wait, long-abandoned work becomes eligible promptly. Healthy multi-delivery progress does not consume the failure budget.

The scheduled five-minute sweep recovers expired owners, marks exhausted work failed, and dispatches due queued jobs. A queued delivery with an acknowledgment gap is eligible for redispatch after ten minutes. Concurrent sweeps may send duplicates; only one owner can compute. Transport delivery history never authorizes another attempt or resets application state. If the database is unavailable before durable disposition, the queue message retries after 60 seconds. Persisted failure/continuation dispositions are acknowledged; the database sweep is the recovery source if queue retries are exhausted. Cloudflare supports per-message acknowledgments and has a 15-minute consumer wall-time limit. [Acknowledgment/retry API](https://developers.cloudflare.com/queues/configuration/batching-retries/), [consumer limits](https://developers.cloudflare.com/queues/platform/limits/).

## Operator inspection

`GET /admin/vector-jobs?state=failed&limit=50` lists durable failed work. `state` also accepts `queued`, `processing`, or `completed`; omission includes all. Follow `nextCursor` as the `after` parameter. The maximum page is 100. Results include document/generation, claimed revision, attempts/failures, progress, lease expiry, next eligible time and a sanitized failure category. Owner tokens and upstream error bodies are not returned.

Inspect the source/current generation and provider availability before repair. Do not reset failure counters with repeated queue sends: they intentionally remain exhausted. A reviewed reprocess under H12 creates a distinct generation/job. If no source/extraction replacement is intended, diagnose the failure and plan an explicit operator repair against the retained generation instead of silently reopening a dead job. Authentication remains H01.

H14 verifies ownership and recovery. H15 separately completes the initial-ingestion outbox transition and source/chunk manifest validation; deploy the complete High lifecycle changes together. No cloud queue was created or modified by this remediation. Local verification uses real SQLite and workerd/D1, with instrumented AI/Vectorize calls; real-provider latency and delivery behavior require an isolated release rehearsal.
